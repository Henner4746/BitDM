# NOTES — assumptions & open questions

## Assumptions Person A baked into the contract
1. The **address** is an opaque `String` produced by the core. The UI only
   displays it (grouped) and validates via `isValidAddress()`. The UI never
   parses keys.
2. **`Message.id`** is generated by the CORE, stable and unique. The UI treats it
   as opaque and uses it to match `MessageStatusUpdate.messageId`.
3. **Timestamps are UTC** `DateTime`.
4. Inbound (decrypted) messages arrive on `incomingMessages`; the core also
   persists them, so `getMessages()` is the source of truth after a restart.
5. Connection/network errors are reported via streams + `MessageStatus.failed`,
   never thrown from methods.
6. `kMaxTextBytes = 4096` (UTF-8). Change it together if you need more.
7. v1 = **single-device, 1:1, text-only**.

## Open questions FOR YOU (Person B)
1. **Address encoding** — canonical string format, length, and display grouping?
   (see DECISIONS.md). This is the one thing blocking final polish on the "My ID"
   and "Add contact" screens.
2. **Message envelope** — define the ciphertext envelope (ratchet header / id / kind).
3. **Settings ownership** — the design has toggles for **read receipts**,
   **screenshot protection**, and a **self-destruct timer**. Do these live in the
   CORE (they change protocol behaviour) or the UI? If core, we add
   `setReadReceiptsEnabled(bool)` / `setDisappearingTimer(...)` to the interface
   TOGETHER. Not in the v1 interface yet — tell me if you want them.
4. **Disappearing messages** — does the core enforce deletion after the timer, or
   is it UI-only for v1? (Design offers off / 1h / 24h / 7d.)
5. **`getMessages` pagination** — I assumed `{limit, before}`; confirm your DB
   supports it (or we simplify).
6. **Safety number** — 60 digits / 12×5 groups OK? You define the `qrPayload` format.
7. **Prekey exhaustion / re-upload** — assumed handled entirely inside the core,
   no UI surface. Confirm.

## Heads-up (important, don't get surprised)
- The **current app UI** (`app/lib/main.dart`) is a self-contained prototype that
  does **NOT yet call `MessengerCore`** — it runs its own in-memory state machine.
  Wiring the UI to the core (swap in `RealMessengerCore`) is **Person A's pending
  task**. The interface in THIS kit is the authoritative contract, and the fake
  matches it exactly — build against `FakeMessengerCore` and your `RealMessengerCore`
  drops straight in.
- `reference/server/relay_server.py` is a working draft (its `test_relay.py`
  passes 4/4). It's **yours** to own and extend (SQLite persistence, TLS, VPS deploy).
- `reference/crypto/crypto_core.py` is a Python proof-of-concept of the
  identity + AES-256-GCM idea — reference only; the real client crypto is libsignal in Dart.
